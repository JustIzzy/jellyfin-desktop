# HANDOFF — Jellyfin Desktop "video invisible until fullscreen toggle"

Written 2026-10-21. A fresh session should be able to continue from this file alone.
Companion detail: `DIAGNOSIS.md` (full evidence trail). Read this file first.

---

## 1. Goal
Owner's Jellyfin Desktop plays audio but shows no picture until fullscreen is toggled
(sometimes twice). Fix it, keeping the embedded web UI and the owner's JS/CSS injection
(Viewfinder / IzzyFlix) working, and audio passthrough intact.

---

## 2. ROOT CAUSE (confirmed by direct experiment)

**QtWebEngine's `WebEngineView` compositor layer is composited opaquely and covers the mpv
video item, even though the page is fully CSS-transparent.**

Proof: a `Ctrl+Shift+W` shortcut was added that toggles `web.visible`. **Hiding the web view
makes the video appear immediately.** Owner confirmed.

The web view sits at `z:100` in `src/ui/webview.qml`, above the `MpvVideoItem`. Its
`backgroundColor` is `#00000000` and every DOM layer over screen centre is `rgba(0,0,0,0)`
(both verified live) — yet the *surface* is still opaque until it is recreated. Any
window-state change recreates it, which is precisely the "toggle fullscreen" workaround.

This explains every previously confusing result:
- plain Win32 libmpv repro works → **no web view**
- minimal Qt Quick + mpvqt test works → **no web view**
- standalone mpv works → **no web view**
- fullscreen toggle fixes it → recreates the web view surface

## 3. Fixes already made (keep these)

### 3a. mpvqt render pump — REAL, PROVEN, SEPARATE BUG
`external/mpvqt/src/mpvrenderer.cpp`, branch `fix/rearm-render-update`, commit `0e20f42`.

`MpvRenderer::render()` never called `mpv_render_context_update()`. libmpv's update callback is
edge-triggered, so mpv fired it once, mpvqt rendered one frame, and the pump stalled forever.
Verified: **2 renders → 1300+ continuous**. This is a genuine upstream KDE bug.
Upstream report drafted (NOT submitted) in `UPSTREAM-mpvqt-issue.md`.

### 3b. `mpv_render_context_report_swap()` — added, same file
mpvqt never told mpv frames were presented. Added after the render call. Correct per the API
contract. (Did not by itself fix the visible symptom, since that was the occlusion above.)

## 4. CURRENT STATE — what is in flight

`src/ui/webview.qml` contains a **work-in-progress fix**: on entering `#/video`, it hides and
re-shows the web view to force surface recreation.

- A single reset fired at URL-change **did not work** — too early; the surface is recreated
  opaque again once playback starts.
- Current code retries **4 times at 1.2 s intervals** (`webSurfaceKick` / `webSurfaceReset`).
- **This was built and launched but the owner has NOT yet reported whether it works.**
  First thing to do: ask, or have them test.

If the retry approach is unreliable, better directions:
1. Trigger the reset off an actual playback signal rather than a timer (e.g. expose
   `videoPlaybackActive` / `playing` from `PlayerComponent` to QML and reset on it).
2. Investigate making the WebEngineView surface transparent properly at creation — look for a
   Qt 6 WebEngine flag/attribute, or set `backgroundColor` again after first paint.
3. Re-parent / re-order so the video item is not under the web view (earlier `z:1000` attempt
   **black-screened the machine** — see warnings below).

## 7. Ruled out — do NOT re-test these

  VF off, so it is a **separate third issue** (see §8)

  trusted clicks on the video area
